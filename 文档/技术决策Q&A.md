## 1. 这次审阅发现了哪些问题？如何修改？

### 1.1 问题与修改清单

| 原问题 | 修改方案 | 修改理由 |
|--------|----------|----------|
| “跳过模块化单体直接微服务”的理由不够企业级 | 保留直接微服务，但明确这是个人项目、自用优先、学习云原生能力的选择 | 企业团队默认不应轻易跳过模块化单体；个人项目可以因学习目标和决策成本低而跳过 |
| 服务拆分容易形成分布式单体 | 明确 task-svc 只负责通用任务生命周期，业务规则仍归 content/interview/research 等业务服务 | 避免所有业务服务变成 thin wrapper，task-svc 变成大单体 |
| `shared/models` 放所有 ORM Model 会重新耦合服务 | shared 只放 DTO、client、事件契约、通用工具；ORM Model 各服务自有 | 微服务必须保持数据模型所有权，否则只是物理拆分 |
| Redis Pub/Sub 不可靠 | 改为 RabbitMQ + Celery，Redis 只做缓存、限流、短状态 | 长任务需要持久化、ack、重试、死信队列 |
| 共享 PostgreSQL 多 schema 的约束不足 | 补充每服务账号、独立 schema、禁止跨 schema join、独立 Alembic migration | 让“单库多 schema”成为过渡方案，而不是单体数据库换皮 |
| Gateway 方案过轻 | 增加 Ingress + FastAPI Gateway 的 Beta 方案，并说明未来何时切 Kong/Envoy/APISIX | 企业级网关能力不只路由，还包括限流、审计、认证、配额 |
| 三高设计偏口号 | 增加可观测指标和 Beta 目标，不再空口承诺固定 QPS | 性能要以压测和指标为准 |
| Python 3.14 偏激进 | 改为 Python 3.12 / 3.13 | 企业项目应优先稳定依赖生态 |
| Go 表格中“JIT”不准确 | 删除不准确表述，改成编译型语言优势 | 避免技术事实错误 |
| 缺安全、可观测性、CI/CD | 新增安全设计、日志指标链路追踪、CI/CD 与交付章节 | 企业级云原生项目必须覆盖这些非功能能力 |

### 1.2 本次修订后的文档定位

本 Q&A 最初记录的是“本地云原生微服务化”的架构修订。2026-07-09 之后，主文档已经升级为 Agent-native 个人 AI 操作系统，因此这里的结论应作为历史决策和工程边界参考，不替代主架构文档。

修订后的文档不是“企业多人团队标准方案”，而是：

> 个人项目在自用优先前提下，采用企业级工程约束进行本地云原生微服务化的设计方案。

这句话很重要。它避免了两个极端：

- 过度企业化：为了“像企业”而引入过多组件，个人维护困难。
- 过度随意：因为是个人项目就忽略任务可靠性、数据边界、安全和观测。

## 2. 个人项目可以跳过模块化单体，直接微服务吗？

### 提问

> 目前就是个人使用，即使要上线也是个人使用，所以直接跳过模块化单体，直接微服务，这样可以吗？

### 回答

可以。对 ChenSage 这个项目来说，这个选择成立。

但要把理由写准确：它不是因为“微服务天然更高级”，而是因为项目约束不同。

### 为什么对本项目可行？

1. **单人决策成本低**  
   企业里服务边界往往受团队边界、发布节奏、数据权限影响。个人项目没有组织协调成本，边界错了可以快速调整。

2. **学习目标明确**  
   你做 Beta1.0 的目标之一就是练云原生、K8s、队列、观测、服务治理。直接微服务能更快进入这些主题。

3. **MVP 已经存在业务模块**  
   不是从零猜边界，而是基于 MVP1.0 的页面、API、数据表和任务链路提炼。

4. **上线也是个人使用**  
   上线规模和合规要求较小，不需要一开始按大型企业 SaaS 强度设计。

### 需要加的限制条件

文档中必须明确：

- 这是个人项目的主动选择，不是企业团队默认建议。
- Beta1.0 不追求服务数量，优先跑通可靠任务、数据迁移、对象存储、观测和部署链路。
- 如果服务拆分导致开发效率明显下降，可以合并服务。

## 3. 为什么要收紧服务边界，避免分布式单体？

### 问题

原设计中有一条链路：

```text
content-svc / interview-svc / research-svc -> task-svc -> model-svc
```

这个链路本身没问题，但如果业务服务只负责接收请求，然后把所有业务参数丢给 task-svc，task-svc 就会变成真正的业务中心。这样会形成分布式单体：

- 部署上是多个服务。
- 业务上仍然是一个大单体。
- 每次改业务都要改 task-svc。
- 服务间通信增加，但隔离收益很小。

### 修改

修订后的边界：

- task-svc：只负责任务生命周期、状态机、队列投递、重试、取消、查询。
- worker：只负责消费队列、调用模型、写回结果。
- content-svc：负责内容创作字段、文体策略、Prompt 组装。
- interview-svc：负责简历面试流程、问题、回答、评价、复盘规则。
- research-svc：负责信息搜集、arXiv 方向、抓取策略、日报编排。

### 判断标准

如果某个服务没有自己的数据模型、状态机、发布理由和运维特征，只是把请求转发给另一个服务，那它不应该拆出来。

## 4. 为什么 shared 不能共享所有 ORM Model？

### 原问题

原文档中 `shared/models/` 放所有 SQLAlchemy ORM Model。这个设计在单体里方便，但在微服务里会造成强耦合。

### 风险

- 一个服务修改表字段，所有服务都要升级 shared 包。
- 服务可以绕过 API 直接读写其他服务表。
- 数据边界失效。
- migration 归属不清晰。
- 最后变成“单数据库 + 多进程”的分布式单体。

### 修改

shared 允许放：

- DTO / Pydantic schema
- OpenAPI 生成 client
- 错误码
- 日志工具
- 配置工具
- 事件契约

shared 不放：

- 全量 ORM Model
- Repository
- 业务 Service
- 数据库 Session

### 原则

每个服务只拥有自己的 ORM Model 和 Alembic migration。跨服务访问通过 API 或事件完成。

## 5. 为什么用 RabbitMQ + Celery 替代 Redis Pub/Sub？

### 原问题

Redis Pub/Sub 是广播通知机制，不是可靠任务队列。

它的问题：

- 消息不持久化。
- 消费者掉线时消息丢失。
- 没有 ack。
- 没有死信队列。
- 不适合长任务重试。

AI 任务往往耗时几十秒到数分钟，且模型 API 可能限流、超时或失败。因此任务系统必须可靠。

### 修改

Beta1.0 选择：

```text
RabbitMQ + Celery Worker
```

### 原因

- RabbitMQ 支持 durable queue。
- Celery 支持任务重试、超时、并发控制。
- 可配置死信队列。
- Python 生态成熟。
- 比自己手写 Redis Streams 消费框架更省心。

### Redis 保留用途

Redis 仍然有价值，但用于：

- 缓存模型配置。
- 缓存 Prompt 模板。
- Gateway 限流计数。
- 短期状态。
- 分布式锁。

不再承担关键任务投递。

## 6. 为什么仍然优先 HTTP + JSON，而不是 gRPC？

### 回答

Beta1.0 继续使用 HTTP + JSON 是合理的。

原因：

- FastAPI 自动生成 OpenAPI，调试简单。
- 单人 Python 技术栈，不需要多语言 `.proto` 契约。
- 服务数量少，同集群内延迟不是主要瓶颈。
- SSE 已能满足任务进度和流式输出。

### 什么时候考虑 gRPC？

只有当某条链路满足以下条件时再考虑：

- 调用频率非常高。
- 请求响应结构稳定。
- 明确测出 HTTP JSON 成为瓶颈。
- 需要多语言强契约。

例如未来 `worker -> model-svc` 变成高频模型网关时，可以只对这一条链路使用 gRPC。

## 7. 为什么 Beta1.0 继续用 Python？

### 回答

继续用 Python 是最合适的。

原因：

- 现有代码资产已经是 Python。
- AI、爬虫、文档解析生态以 Python 最成熟。
- 项目瓶颈主要是外部模型 API 网络 IO，不是本地 CPU。
- FastAPI + Pydantic + SQLAlchemy 足够支撑 Beta1.0。

### 为什么不用 Go？

Go 适合高并发、低资源、网络服务和基础设施组件。但本项目当前更需要：

- 快速迭代。
- 复用现有代码。
- 接入 AI SDK 和解析库。

未来可以把高频、低延迟、稳定边界的 model gateway 单独用 Go 实现。

### 为什么不用 Java？

Java / Spring 在大型企业业务系统里成熟，但对本项目初期有几个成本：

- 重写成本高。
- AI SDK 和文档处理生态不如 Python 直接。
- 内存和启动成本更高。
- Spring Cloud 的很多能力在 K8s 中已有替代方案。

未来如果认证、权限、网关治理复杂化，可以考虑 auth-svc 或 gateway 用 Java。

## 8. 为什么数据库采用 PostgreSQL 单实例多 schema？

### 回答

这是个人项目 Beta 阶段的折中方案。

完全企业微服务通常会强调“每服务独立数据库”。但个人项目一次维护 7 个数据库实例没有必要，成本高于收益。

因此 Beta1.0 采用：

```text
一个 PostgreSQL 实例，多个 schema，每个服务一个 schema
```

### 必须遵守的约束

- 每个服务使用独立数据库账号。
- 每个账号只拥有自己的 schema 权限。
- 禁止跨 schema join。
- 跨服务读取走 API。
- 事件同步用 RabbitMQ。
- migration 按服务独立管理。

如果不遵守这些约束，多 schema 也会退化成单体数据库。

## 9. 为什么不一开始就上 Kong、Envoy 或 Java Gateway？

### 回答

Beta1.0 的目标是先跑通架构，不是先把所有企业组件堆满。

初期推荐：

```text
Nginx Ingress + FastAPI gateway
```

FastAPI gateway 负责：

- 业务路由。
- 用户上下文注入。
- 简单认证校验。
- 请求 ID。
- 简单限流。

### 什么时候升级专业网关？

当出现这些需求时：

- API Key 管理。
- 多租户配额。
- 复杂限流。
- 插件化鉴权。
- 灰度路由。
- API 审计。
- 多环境统一入口。

届时考虑 Kong、Envoy、APISIX 或 Traefik。

## 10. 为什么要补安全、可观测性和 CI/CD？

### 原问题

原文档重点写了服务拆分和技术栈，但企业级云原生项目不仅是“拆服务 + K8s”。

还必须回答：

- 出问题怎么发现？
- 任务卡住怎么定位？
- 模型 API 费用怎么统计？
- 用户和 API Key 怎么保护？
- 镜像怎么构建和回滚？
- 数据怎么备份？

### 修改

架构文档新增：

- 安全设计：认证、授权、Secret、SSRF 防护、审计。
- 可观测性：日志、指标、Trace、告警。
- CI/CD：测试、构建、镜像扫描、部署和回滚。
- SLO 指标：不再空口承诺 QPS，而是先建立可测指标。

### 理由

这些是云原生项目真正进入“工程化”的关键。没有它们，K8s 只是运行容器的地方，不等于企业级架构。

## 11. 修改后的 Beta1.0 落地优先级是什么？

### 优先级 1：底座可靠

1. PostgreSQL 替换 SQLite。
2. RabbitMQ + Celery 替换本地线程。
3. MinIO 替换本地文件路径。
4. Redis 用于缓存和限流。
5. Docker Compose 一键启动。

### 优先级 2：服务边界

1. gateway
2. task-svc + worker
3. model-svc
4. file-svc
5. research-svc
6. content-svc
7. interview-svc
8. auth-svc

auth-svc 可以早建，但个人本地使用可以先简单实现，不必一开始做复杂 RBAC。

### 优先级 3：工程化

1. Alembic migration。
2. JSON 日志。
3. Prometheus 指标。
4. OpenTelemetry Trace。
5. GitHub Actions。
6. 镜像扫描。
7. 基础测试。

### 优先级 4：Kubernetes

1. kind 本地集群。
2. Helm/Kustomize。
3. readiness/liveness probes。
4. 滚动更新。
5. HPA 验证。

### 最终判断

修订后的方案保留了“个人项目直接微服务”的学习目标，但用更严格的企业级约束限制风险：

- 不为了拆而拆。
- 不共享 ORM。
- 不用不可靠 Pub/Sub 跑关键任务。
- 不忽略安全、观测和交付。
- 不对性能做未经验证的承诺。

这比原文档更适合继续作为 ChenSage_Beta1.0 的架构设计依据。

## 12. AgentOS 调整后，哪些决策需要同步？

### 回答

AgentOS 版本不是推翻原来的工程化决策，而是把产品核心从“业务微服务集合”调整为“Agent 任务平台”。因此以下规则需要同步：

- Beta1.0 的范围是一次有意的平台底座验证，不再只按窄功能 MVP 评价范围大小。
- 第一版可以把 `agent-orchestrator`、`agent-harness`、`loop-engine`、`context-engine` 放在同一个 `agent-svc` 内部，但边界要按未来独立能力设计。
- `task-svc` 是任务状态唯一事实源，`worker` 和 `agent-svc` 只能通过 API 或事件推进状态。
- `model-svc` 是唯一模型调用入口，模型调用不注册成普通工具。
- `tool-registry` 管非模型工具，例如搜索、arXiv、文件解析、导出、记忆检索和评估检查。
- 活记忆第一版采用“自动临时记忆 + 用户确认长期记忆”的策略，避免错误记忆静默长期生效。
- PostgreSQL 单实例多 schema 的约束继续有效：独立账号、独立 migration、禁止跨 schema join、shared 不放 ORM Model。
- 安全默认值需要前置：Secret 只由授权服务读取，外部请求白名单，文件访问受限，日志和 trace 脱敏。
