## 1. 总体定位

ChenSage 从原来的“本地云原生微服务平台”升级为：

```text
ChenSage AgentOS
个人 AI 任务中枢 + 多 Agent 编排 + 活记忆 + 工具协议 + 可靠任务执行
```

新版 ChenSage 不再只是“内容生成、信息搜集、面试训练、arXiv 日报”等功能集合，而是一个面向个人知识工作者的 Agent 平台和对话式内容生产中枢。

核心运行方式：

```text
用户提出目标
  -> 系统理解意图
  -> planner-agent 拆解任务
  -> 多个 subagent 协作
  -> 调用工具和模型
  -> 读写活记忆
  -> 形成结果
  -> 自动评估、解释理由、定位问题并给出修改建议
  -> 把用户反馈、评价理由和生产经验沉淀回知识库 / 活记忆 / 提示词模板
```

原架构中的 PostgreSQL、RabbitMQ、Redis、MinIO、Docker Compose、OpenTelemetry 等能力继续保留，但它们不再是产品叙事中心，而是 Agent 平台的可靠工程底座。

## 2. 设计目标与边界

### 2.1 设计目标

Beta1.0 重点建立七类能力：

- Agent 编排：支持任务拆解、多 Agent 协作、失败恢复和状态同步。
- Agent Harness：统一 Agent 运行套件，减少重复实现。
- Loop Engine：控制 plan、act、observe、evaluate、revise、stop 的执行循环。
- Context Engine：管理上下文组装、压缩、隔离、来源和任务快照。
- Living Memory：建立可更新、可治理、可检索、可过期的活记忆系统。
- Knowledge Base：沉淀历史内容、资料来源、高质量案例、用户偏好和评价经验。
- Tool Registry：统一管理内部工具和 MCP-style 工具。
- Content Evaluation Feedback：对生成内容给出评分、理由、问题定位、修改建议和学习沉淀建议。
- Conversation Workbench：提供统一对话式内容生产窗口，按任务调取知识库和 Agent。
- Reliable Task Queue：用 RabbitMQ + Celery 支撑可靠长任务。

Beta1.0 的范围有意偏向“首次平台底座验证”。它不是只做一个窄功能 demo，而是用第一条完整 Agent 任务链路验证前端、网关、任务队列、Agent 运行、模型调用、工具、记忆、评估和观测这些平台边界能否协同工作。

实现原则是：

- 目录、接口、数据所有权按平台边界设计。
- 部署形态可以先合并，能力边界不能混乱。
- 第一版允许 `agent-orchestrator`、`agent-harness`、`loop-engine`、`context-engine` 同在 `agent-svc` 内部实现。
- `living-memory-svc`、`tool-registry`、`eval-svc`、`policy-svc` 可以先做最小可用能力，但要保留独立服务边界。
- 验证目标不是服务数量，而是一条端到端任务链路可运行、可追踪、可恢复、可治理。

### 2.2 设计边界

Beta1.0 不是目标：

- 不直接做大型多人企业 SaaS。
- 不把每个 Agent 一开始都拆成独立微服务。
- 不让每个 Agent 自己管理模型 Key、工具权限和记忆读写。
- 不追求一次性实现完整通用 AGI 平台。
- 不放弃本地开发效率，Docker Compose 仍是第一落地点。
- 不为了拆服务而拆服务；如果某个能力没有独立数据、状态和运维特征，第一版可以先作为模块存在。

### 2.3 架构原则

- Agent 是产品核心，微服务是工程组织方式。
- Orchestrator 负责调度和协作，不吞掉所有业务逻辑。
- Harness 统一运行约束，Agent 只表达角色能力。
- Memory 必须可治理，不能无限静默写入。
- Tool 必须 schema 化、权限化、可审计。
- Model 调用统一走 `model-svc`，避免 Key 和 Provider 逻辑散落。
- 长任务进入 `task-svc` + RabbitMQ + Worker，不阻塞 HTTP 请求。
- `task-svc` 是任务状态唯一事实源，其他服务只能通过 API 或事件推进状态。
- 模型调用不作为普通工具暴露给 Agent，避免绕过模型预算、审计和 Key 管理。

### 2.4 Beta1.0 产品功能范围

Beta1.0 不是脱离 MVP 功能另造平台，而是把 MVP 已验证过的个人知识工作能力迁移到 AgentOS 架构中，让原有功能获得统一任务、可靠队列、模型配置、提示词模板、文件解析、导出、记忆和可观测能力。

第一阶段产品功能包括：

| 产品功能 | 功能范围 |
|------|------|
| 内容创作 | 支持论文、专利、小说、剧本、歌词、小红书、知乎、公众号等内容生成与改写 |
| 模拟面试 | 基于简历和岗位描述生成简历分析、面试问题、回答评价和复盘报告 |
| 信息搜集 | 支持单 URL / PDF / JSON / RSS、批量多任务、站内信息发现与汇总报告 |
| arXiv 日报 | 支持研究方向管理、关键词 / 分类配置、按日期和篇数拉取论文、收藏论文、按范围生成日报 |
| 模型设置 | 支持 OpenAI-compatible API 配置、默认模型、连通性测试 |
| 提示词模板 | 支持按任务类型维护模板，并在信息搜集、arXiv 日报、内容创作等功能中复用 |
| 文件管理 | 支持上传并解析 PDF、DOCX、TXT、MD |
| 历史任务与导出 | 支持统一查看任务、重试、导出 Markdown |
| 对话式生产窗口 | 支持在统一对话窗口中理解任务、调取知识库、选择模板和生成内容 |
| 知识库沉淀 | 支持沉淀历史内容、资料来源、高质量案例、用户偏好和评价经验 |
| 内容评价与反馈 | 支持评分、评分理由、问题定位、修改建议、版本对比和经验沉淀 |

产品功能与 AgentOS 模块映射：

| MVP 功能 | 主要 Agent / 服务 | 关键依赖 |
|------|------|------|
| 内容创作 / 改写 | `content-agent`, `task-svc`, `model-svc` | prompt registry, Markdown export, eval report |
| 模拟面试 | `interview-agent`, `file-svc`, `eval-svc` | 简历解析, JD 输入, 回答评价, 复盘报告 |
| 信息搜集 | `research-agent`, `tool-registry`, `task-svc` | URL / PDF / JSON / RSS 工具, 批量任务, 汇总导出 |

| 提示词模板 | `agent-svc` 内 prompt registry | 任务类型、模板版本、变量 schema、复用策略 |
| 文件管理 | `file-svc`, `tool-registry` | MinIO, PDF / DOCX / TXT / MD 解析 |
| 历史任务与导出 | `task-svc`, `file-svc` | task event, retry, Markdown export |
| 对话式生产窗口 | `conversation-agent`, `agent-orchestrator`, `context-engine` | 任务理解, 澄清问题, 知识检索, Agent 路由 |
| 知识库沉淀 | `knowledge-base-svc`, `living-memory-svc` | 历史内容, 资料来源, 高质量案例, 用户偏好, pgvector |
| 内容评价与反馈 | `eval-svc`, `memory-agent`, `prompt-optimizer` | 评分, 理由, 问题定位, 修改建议, 经验沉淀 |

实现顺序见 `文档/功能开发顺序.md`。产品功能开发应优先围绕可运行的任务主链路展开，而不是孤立实现页面或单个工具。

### 2.5 配置管理边界

Beta1.0 需要从一开始明确配置和 Secret 的归属，尤其是大模型 API Key。

配置目录：

```text
.env.example                   根级本地环境变量示例
config/app/                    应用级非敏感配置
config/models/                 模型 Provider 示例配置，不放真实 API Key
config/prompts/                内容、面试、研究、arXiv 等提示词模板
infra/docker/.env.example      Docker Compose 本地依赖配置示例
services/*/config/             服务自己的配置读取边界
```

配置规则：

- 真实 `.env` 不提交。
- 真实 API Key 不写入 YAML、README、代码或测试样例。
- `model-svc` 是唯一读取模型 Provider Secret 的服务。
- 前端模型设置页只调用 `model-svc`，不直接保存或读取模型 API Key。
- `config/models/providers.example.yaml` 只声明 Provider 结构、环境变量名、模型列表和预算策略。
- `config/prompts/` 存放可版本化提示词模板，模板不包含用户隐私和真实任务数据。
- 生产配置只提交 `production.example.yaml`，真实 `production.yaml` 不入库。

## 3. 核心概念解释

### 3.1 Agent-native

Agent-native 表示系统以 Agent 的规划、执行、观察、评估、修正为核心运行模型。传统应用通常是“用户点按钮 -> 后端执行固定逻辑”，Agent-native 系统则是“用户提出目标 -> 系统动态规划路径 -> 调用多个 Agent 和工具完成目标”。

对 ChenSage 来说，Agent-native 不是在旧功能上套一个聊天入口，而是让内容创作、研究、面试、文件处理、复盘和记忆沉淀都进入同一个 Agent 任务体系。

### 3.2 Agent Orchestrator

`agent-orchestrator` 是新版核心服务，负责任务理解、Agent 调度、执行计划管理、Agent 间协作、任务状态同步。

它解决的问题是：

- 当前目标应该由哪些 Agent 完成。
- Agent 之间按什么顺序协作。
- 哪一步需要工具、模型、记忆或人工审批。
- 某一步失败后应该重试、降级、改计划还是终止。

它不应该直接写所有业务逻辑，否则会变成新的超级单体。

### 3.3 Agent Harness

`agent-harness` 是每个 Agent 的统一运行套件。Agent 不应该各自重复实现工具调用、记忆访问、模型路由、输出校验、重试、日志和权限。

Harness 包含：

```text
prompt template
tool permissions
memory access
model routing
output schema validation
retry policy
cost limit
trace logging
human approval
```

### 3.4 Loop Engine

`loop-engine` 负责循环执行机制。

典型 loop：

```text
plan -> act -> observe -> evaluate -> revise -> stop
```

必须内置限制：

```text
max_steps
max_tokens
max_cost
max_duration
stop_condition
human_approval_required
```

这些限制用于防止 Agent 无限循环、重复调用工具、烧 token 或执行高风险动作。

### 3.5 Context Engine

`context-engine` 负责上下文工程。它决定 Agent 每一步能看到什么、不能看到什么、哪些信息需要压缩、哪些信息必须带来源。

包含：

```text
context assembly
context compression
context isolation
source provenance
task snapshot
agent scratchpad
```

上下文不是越多越好。过多上下文会增加成本、污染判断，甚至把无关历史带入当前任务。

### 3.6 Living Memory

`living-memory-svc` 是活记忆系统。它不是普通聊天历史，而是会持续更新、合并、过期、冲突检测，并被用户治理的动态记忆。

记忆类型：

```text
working memory      当前任务临时记忆
episodic memory     任务经历和事件
semantic memory     稳定知识和用户偏好
procedural memory   做事方法和流程经验
reflective memory   Agent 复盘总结
governed memory     用户确认、冻结、删除的记忆
```

### 3.7 Knowledge Base

`knowledge-base-svc` 负责沉淀可复用知识。它和活记忆不同：活记忆更偏用户偏好、任务经验和运行时记忆；知识库更偏内容资产、资料来源、高质量案例、评价经验和可检索文档。

知识库内容包括：

```text
historical outputs      历史生成内容和版本
source materials        URL / PDF / JSON / RSS / arXiv 等资料来源
high-quality examples   用户确认过的高质量内容案例
style preferences       写作风格、平台表达、禁用表达
evaluation insights     评分理由、问题定位、修改建议、复盘经验
domain notes            研究方向、主题资料、长期知识
```

知识库不是让模型直接训练参数，而是通过检索、上下文注入、模板改进和记忆治理，让系统在后续任务中更懂用户的内容标准。

### 3.8 Conversation Workbench

对话式生产窗口是 Beta 的统一内容生产入口。用户可以直接描述目标，系统负责理解任务类型、提出澄清问题、选择知识库、选择 Agent 和生成内容。

典型流程：

```text
user message
  -> conversation-agent 理解目标和约束
  -> context-engine 选择相关知识库、历史任务、模板和记忆
  -> planner-agent 拆解任务
  -> content / research / interview / arXiv Agent 执行
  -> eval-svc 输出评价反馈报告
  -> 用户选择采纳、修改、重写或沉淀经验
```

对话窗口不是普通聊天，而是“内容集中生产窗口”：左侧可看知识库和历史任务，中间对话生成，右侧展示来源、评分理由、问题定位、修改建议和版本历史。

### 3.9 Content Evaluation & Learning Feedback

`eval-svc` 不只是打分服务，而是内容评价与学习反馈系统。它必须输出结构化评价报告：

```text
scores              分维度评分
score_reasons       每个分数的理由
issue_locations     问题位置，例如段落、句子、结构、引用
revision_advice     修改建议
usable_highlights   值得保留的优点
learning_candidates 可沉淀到知识库、活记忆、提示词模板的经验
```

评价维度可以包括：

- 事实准确性。
- 结构完整性。
- 风格匹配度。
- 平台适配度。
- 引用和来源完整性。
- 用户目标满足度。
- 可直接使用度。

这些评价结果会进入任务历史，并由 `memory-agent` 判断哪些经验值得进入活记忆或知识库。多次评价形成稳定模式后，`prompt-optimizer` 可以提出提示词模板优化建议，但需要用户确认后生效。

### 3.10 Tool Registry

`tool-registry` 是工具注册中心。它统一管理内部工具和 MCP-style 工具。

示例工具：

```text
web_search
arxiv_search
file_parse
pdf_export
markdown_export
database_query
memory_search
```

每个工具必须具备权限、输入 schema、输出 schema、审计日志和调用成本。

### 3.11 Eval Service

`eval-svc` 负责评估 Agent 输出质量，包括：

- 事实性检查。
- 格式检查。
- 引用来源检查。
- 完整性检查。
- 风格一致性检查。
- 是否满足用户目标。
- 分维度评分。
- 评分理由。
- 问题定位。
- 修改建议。
- 学习沉淀建议。

### 3.12 Policy Service

`policy-svc` 负责权限、安全、审批和成本控制，包括：

- 敏感工具调用前审批。
- 外部请求白名单。
- 文件访问权限。
- 模型预算限制。
- 记忆写入规则。
- 高风险操作拦截。

| 可观测层 | OpenTelemetry, Prometheus, Grafana, Loki | Trace、指标、日志、成本和质量观测 |

## 5. 核心模块设计

### 5.1 gateway

统一入口，负责：

- 认证和用户上下文。
- 限流。
- 请求 ID 和 trace 上下文注入。
- API 路由。
- SSE / WebSocket 代理，供任务进度和 Agent step 事件展示。

第一版可以继续使用 FastAPI，后期再考虑 Kong、Envoy 或 APISIX。

### 5.2 agent-orchestrator

新版核心服务，负责：

- 理解用户目标。
- 创建执行计划。
- 选择 Agent。
- 管理 Agent 间协作。
- 同步任务状态。
- 决定失败后的重试、改计划、降级或终止。
- 调用 `policy-svc` 判断是否需要人工审批。
- 调用 `eval-svc` 评估阶段性输出和最终输出。

边界约束：

- 不直接保存所有业务数据。
- 不直接调用外部模型 Key。
- 不直接执行所有工具。
- 不替代各 Agent 的专业能力。
- 不作为任务状态唯一事实源；任务状态以 `task-svc` 为准。
- 不直接写最终任务结果；通过 `task-svc` 记录阶段事件、结果索引和终态。

### 5.3 agent-harness

Agent 运行套件，负责：

- 加载 Agent prompt template。
- 注入模型路由策略。
- 注入工具权限。
- 注入记忆访问策略。
- 校验输出 schema。
- 执行 retry policy。
- 控制 cost limit。
- 写入 trace logging。
- 触发 human approval。

每个 Agent 只定义角色、目标、输入输出结构和可用工具，不重复写平台逻辑。

### 5.4 loop-engine

Loop Engine 负责一次 Agent 任务的循环推进。

核心对象：

| 对象 | 含义 |
|------|------|
| `loop_run` | 一次循环执行实例 |
| `loop_step` | 单步 plan / act / observe / evaluate / revise |
| `stop_condition` | 停止条件 |
| `budget` | token、cost、duration、step 限制 |
| `approval_gate` | 人工审批卡点 |

### 5.5 context-engine

Context Engine 负责：

- 组装任务上下文。
- 压缩历史和中间结果。
- 隔离不同 Agent 的 scratchpad。
- 保留 source provenance。
- 生成 task snapshot。
- 控制哪些 memory 可以进入当前上下文。

### 5.6 living-memory-svc

活记忆服务，负责：

- 写入新记忆。
- 检索相关记忆。
- 合并重复记忆。
- 检测冲突。
- 过期和降权。
- 用户确认、冻结、删除。
- 生成 memory snapshot。

### 5.7 knowledge-base-svc

知识库服务，负责：

- 管理历史生成内容和版本。
- 管理用户确认的高质量案例。
- 管理来源资料、引用、摘要和文档分片。
- 管理评价反馈沉淀出的经验条目。
- 支持按任务类型、主题、来源、质量分、用户偏好检索。
- 通过 pgvector 提供语义检索。
- 向 context-engine 返回带来源、置信度和适用范围的知识片段。

边界约束：

- 不替代 living-memory-svc 的用户长期偏好治理。
- 不静默把所有生成结果都提升为高质量知识。
- 长期有效的风格偏好、禁用表达、流程经验需要用户确认或达到明确治理规则。

### 5.8 tool-registry

工具注册中心，负责：

- 工具注册和发现。
- 输入输出 schema 管理。
- 权限和审批策略。
- 工具调用审计。
- 成本统计。
- MCP-style 工具适配。

### 5.9 model-svc

统一模型服务，负责：

- 模型 Provider 管理。
- API Key 管理。
- 模型路由。
- 限流。
- 失败重试。
- 成本统计。
- 模型调用 trace。

不要让每个 Agent 自己直接调用模型。

`model-svc` 是唯一模型调用入口。模型调用不要注册成普通 `model_call` 工具，否则 Agent 可能绕过模型预算、Provider 路由、Key 管理和统一审计。

### 5.10 task-svc

`task-svc` 继续保留，负责任务生命周期：

```text
queued
running
waiting_approval
succeeded
failed
cancelled
expired
```

它不处理业务逻辑，只管理任务状态、进度、重试、取消、查询、结果索引。

状态所有权规则：

- `task-svc` 是 task、task_event、task_result 的唯一写入入口。
- `agent-orchestrator` 生成计划和下一步决策，但不直接成为状态数据库。
- `worker` 消费 RabbitMQ 后，通过 `task-svc` API 或事件推进状态。
- 用户取消、审批通过、审批拒绝统一进入 `task-svc` 状态机。
- 所有状态迁移必须记录操作者、来源、trace_id 和原因。

### 5.11 eval-svc

评估服务负责生成内容评价与学习反馈报告：

- 事实性检查。
- 格式检查。
- 引用来源检查。
- 完整性检查。
- 风格一致性检查。
- 是否满足用户目标。
- 分维度评分。
- 给出每个分数的理由。
- 定位具体问题位置。
- 给出修改建议。
- 标出值得保留的优点。
- 生成可沉淀经验候选项。
- 生成 eval report。

eval report 至少包含：

```text
scores
score_reasons
issue_locations
revision_advice
source_risks
usable_highlights
learning_candidates
```

边界约束：

- 不直接修改最终内容。
- 不自动修改提示词模板。
- 不自动把评价经验写入长期知识库；写入前应经过 memory-agent 判断和治理规则。

### 5.12 prompt-optimizer

提示词优化器负责从多次评价反馈中发现稳定问题，并提出模板优化建议。

它不直接在线训练模型参数，而是通过以下方式让系统“学习”：

- 发现某类任务经常出现的问题。
- 汇总高分内容的共同结构。
- 提取用户偏好的表达方式。
- 提出 prompt template 的变量、约束和示例改进。
- 将建议提交给用户确认或进入待审核状态。

边界约束：

- 不静默覆盖现有模板。
- 不把一次低分结果直接固化为长期规则。
- 模板优化建议需要保留来源任务、评分理由和示例证据。

### 5.13 policy-svc

策略服务负责：

- 敏感工具调用前审批。
- 外部请求白名单。
- 文件访问权限。
- 模型预算限制。
- 记忆写入规则。
- 高风险操作拦截。

## 7. 任务执行与 Agent Loop

### 7.1 任务链路

```text
用户输入目标
  -> gateway 创建请求上下文
  -> conversation-agent 理解目标、澄清约束、判断任务类型
  -> context-engine 检索活记忆、知识库、历史任务和提示词模板
  -> agent-orchestrator 创建 task
  -> planner-agent 生成计划
  -> task-svc 记录 queued / running
  -> RabbitMQ 投递长任务
  -> worker 执行 Agent loop
  -> agent-harness 调 model-svc / tool-registry / knowledge-base-svc / living-memory-svc
  -> eval-svc 生成评分、理由、问题定位、修改建议
  -> memory-agent 判断评价经验是否进入活记忆或知识库
  -> task-svc 标记 succeeded / failed
```

### 7.2 Loop 步骤

```text
plan
  生成当前阶段计划
act
  调用模型、工具、记忆或其他 Agent
observe
  读取工具返回、模型输出、错误和外部状态
evaluate
  评估是否满足目标、是否需要修正
revise
  调整计划、重试、换工具或请求审批
stop
  达成目标、失败终止、等待审批或达到限制
```

### 7.3 执行限制

必须支持：

- `max_steps`
- `max_tokens`
- `max_cost`
- `max_duration`
- `stop_condition`
- `human_approval_required`

### 7.4 任务状态

| 状态 | 含义 |
|------|------|
| `queued` | 已创建，等待执行 |
| `running` | 正在执行 |
| `waiting_approval` | 等待用户审批 |
| `succeeded` | 执行成功 |
| `failed` | 执行失败 |
| `cancelled` | 用户或系统取消 |
| `expired` | 超时或审批过期 |

## 8. 活记忆系统

### 8.1 记忆类型

| 类型 | 含义 |
|------|------|
| working memory | 当前任务临时记忆 |
| episodic memory | 任务经历和事件 |
| semantic memory | 稳定知识和用户偏好 |
| procedural memory | 做事方法和流程经验 |
| reflective memory | Agent 复盘总结 |
| governed memory | 用户确认、冻结、删除的记忆 |

### 8.2 核心表

```text
memories
memory_events
memory_links
memory_conflicts
memory_feedback
memory_snapshots
```

### 8.3 memory 字段

每条 memory 建议包含：

```text
id
user_id
scope
type
content
summary
source_refs
confidence
importance
status
created_by_agent
last_used_at
expires_at
version
embedding
```

### 8.4 记忆治理

活记忆必须支持用户治理：

- 用户确认：重要偏好或长期事实需要确认。
- 用户冻结：冻结后的记忆不被自动覆盖。
- 用户删除：用户可删除不需要或错误的记忆。
- 冲突检测：新记忆与旧记忆冲突时进入待确认状态。
- 过期降权：长期不用或低置信度记忆逐渐降低权重。

### 8.5 Beta1.0 最小记忆策略

第一版不要让所有记忆都自动长期生效。推荐分层：

| 层级 | 写入方式 | 默认状态 |
|------|----------|----------|
| working memory | Agent 自动写入 | 任务结束后过期或归档 |
| episodic memory | Agent 自动提议 | 可检索但低权重 |
| semantic memory | Agent 提议，用户确认 | confirmed 后长期生效 |
| procedural memory | Agent 提议，用户确认 | confirmed 后进入流程经验 |
| governed memory | 用户直接确认、冻结或删除 | 最高优先级 |

关键规则：

- 长期偏好、身份信息、工作方式、敏感事实必须用户确认后生效。
- `memory-agent` 只能提出写入建议，不能静默覆盖 governed memory。
- 冲突记忆进入 `pending_confirmation`，不能直接覆盖旧记忆。
- 检索时必须带 `source_refs`、`confidence`、`status`，Context Engine 根据状态决定是否进入上下文。

## 10. 数据架构

### 10.1 PostgreSQL schema

```text
PostgreSQL
  auth_schema
  task_schema
  agent_schema
  memory_schema
  knowledge_schema
  model_schema
  file_schema
  eval_schema
  audit_schema
```

Beta1.0 采用单 PostgreSQL 实例、多 schema 的折中方案，但必须遵守微服务数据边界：

- 每个服务使用独立数据库账号。
- 每个账号只拥有自己的 schema 权限。
- 每个服务维护自己的 SQLAlchemy ORM Model 和 Alembic migration。
- 禁止跨 schema join。
- 跨服务读取通过 API 或事件同步完成。
- shared 包只放 DTO、client、事件契约、错误码和通用工具，不放全量 ORM Model、Repository、数据库 Session。
- 如果某个模块暂时和其他模块同进程部署，也要按未来服务边界隔离 schema 和 migration。

## 12. 安全、策略与审批

### 12.1 策略控制

`policy-svc` 控制：

- 外部请求白名单和黑名单。
- 文件访问范围。
- 数据库查询范围。
- 模型预算。
- 工具调用权限。
- 记忆写入权限。
- 高风险操作阻断。

Beta1.0 默认策略：

- 外部网络访问默认需要白名单；未知域名进入审批或拒绝。
- 文件工具只能访问用户上传目录、任务工作目录和系统明确授权目录。
- 防止 SSRF：禁止访问内网保留地址、metadata endpoint、本机管理端口和未授权协议。
- API Key 和 Provider Secret 只由 `model-svc` 读取，其他 Agent 和工具不能直接读取。
- 日志和 trace 默认脱敏，不记录完整 API Key、Cookie、Authorization header、原始敏感文件内容。
- 高成本模型、批量外部请求、删除/覆盖/导出等动作必须经过预算或审批规则。
- 记忆写入按类型分级，长期记忆和 governed memory 必须可回滚、可删除、可审计。

### 12.2 人工审批

以下情况建议进入 `waiting_approval`：

- 调用高成本模型或超出预算。
- 写入长期 governed memory。
- 访问敏感文件。
- 发起外部网络请求到未知域名。
- 执行不可逆导出、删除或覆盖动作。

### 12.3 审计

审计日志至少覆盖：

- 用户登录和失败登录。
- Agent 计划和关键决策。
- 工具调用。
- 模型调用和成本。
- 记忆写入、修改、删除、冻结。
- 文件上传、解析、导出。
- 审批通过和拒绝。

## 15. 风险与应对

| 风险 | 等级 | 应对 |
|------|------|------|
| Agent 无限循环和成本失控 | 高 | loop-engine 强制 `max_steps`、`max_tokens`、`max_cost`、`max_duration` |
| Orchestrator 变成超级单体 | 高 | Orchestrator 只做调度，业务能力放 Agent 和平台服务 |
| 记忆污染或错误记忆长期生效 | 高 | 引入 confidence、source_refs、冲突检测、用户确认、过期降权 |
| 知识库污染或低质量内容被反复引用 | 高 | 区分历史版本、高质量案例、待确认经验；检索时带质量分、来源和状态 |
| 评价反馈被过度固化为错误规则 | 高 | learning candidate 进入待确认，不从单次评价直接修改模板或长期记忆 |
| 工具调用越权 | 高 | tool-registry + policy-svc 统一权限和审批 |
| 每个 Agent 重复实现平台能力 | 中 | 所有 Agent 挂 agent-harness |
| 过早拆分过多微服务 | 中 | 第一版使用 agent-svc，边界稳定后再拆 |
| 模型 Provider 逻辑散落 | 中 | 所有模型调用统一经过 model-svc |
| 任务失败难排查 | 中 | Agent trace、tool call trace、eval report、结构化日志 |
| 本地工程复杂度过高 | 中 | Compose 优先，K8s 后置 |

## 16. 阶段路线图

### 阶段 0：架构文档重写

- 项目定位从“云原生微服务化”改成“Agent-native 个人 AI 操作系统”。
- README 和主架构文档同步 AgentOS 概念。
- 明确 Agent Orchestrator、Harness、Loop、Memory、Tool、Eval、Policy 的边界。

### 阶段 1：基础底座

- PostgreSQL + pgvector。
- RabbitMQ。
- Redis。
- MinIO。
- Docker Compose。
- 基础 gateway、model-svc、task-svc、worker。
- 建立前后端、服务、worker、shared、infra 的目录骨架。
- 明确 task、agent、memory、tool、model、file、audit 的 schema 所有权。

### 阶段 2：Agent MVP

实现：

```text
agent-orchestrator
agent-harness
loop-engine
model-svc
task-svc
worker
tool-registry 最小能力
knowledge-base-svc 最小能力
living-memory-svc 最小能力

```

先跑通一个完整任务：


```text
ChenSage AgentOS
```
