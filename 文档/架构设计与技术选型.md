## 1. 项目定位与设计边界

### 1.1 项目定位

晨枢 AI (ChenSage) 是一个面向个人知识工作者的 AI 任务中枢平台。Beta1.0 的目标不是立刻做多人企业 SaaS，而是把 MVP1.0 从本地单体逐步演进为可容器化、可观测、可扩展、可部署的本地云原生系统。

Beta1.0 的核心目标：

- 保持个人自用体验稳定，不为了“微服务形式”牺牲可维护性。
- 引入 Docker、Docker Compose、Kubernetes(kind)、PostgreSQL、RabbitMQ、Redis、MinIO 等云原生基础设施。
- 建立清晰的服务边界、数据边界、任务队列、日志、监控、CI/CD 和安全基线。
- 为未来上线个人版 SaaS 或小规模私有部署预留演进空间。

### 1.2 当前 MVP1.0 已有资产

| 资产 | 规模 |
|------|------|
| 后端 API 端点 | 约 45 个 |
| 前端页面路由 | 约 10 个 |
| 数据库表 | 约 16 张 |
| Python 代码量 | 约 8,000 行 |
| TypeScript 代码量 | 约 5,000 行 |
| Prompt 模板 | 内置模板 + 数据库存储模板 |

### 1.3 当前 MVP1.0 架构

```text
Browser
  -> Next.js Web (localhost:3000)
  -> FastAPI API (localhost:8000)
  -> SQLite / local files / local background thread
```

当前问题：

- 后端是单体应用，任务执行、模型调用、文件解析、信息搜集都在同一进程。
- 后台任务使用本地线程，缺少可靠队列、重试、死信和任务恢复机制。
- SQLite 适合单机 MVP，不适合长期并发写和云原生部署。
- 文件、导出、日志都在本地磁盘，不利于多副本部署。
- 暂无正式认证、授权、审计和服务间鉴权。

## 2. 架构演进策略

### 2.1 是否可以跳过模块化单体，直接微服务？

可以，但必须明确前提。

企业默认路径通常是：

```text
Monolith -> Modular Monolith -> Microservices
```

对多人团队来说，模块化单体能先验证领域边界，降低分布式系统复杂度。因此，企业项目不应轻易跳过这一阶段。

本项目可以跳过模块化单体，是因为它满足以下特殊前提：

- 当前是个人项目，服务边界由单人决策，不存在团队组织边界协商成本。
- 项目目标包含学习云原生和微服务能力，微服务本身是学习目标之一。
- MVP 已经有较清楚的业务模块，可作为拆分参考。
- 初期部署仍以本地 Docker Compose / kind 为主，外部用户规模较小。

因此，本文档的结论是：

> ChenSage_Beta1.0 可以直接微服务化，但这不是企业项目的通用默认建议，而是个人项目在学习目标和自用场景下的主动选择。

### 2.2 演进原则

- 先拆运行形态，再拆所有业务：优先把 API、Web、Worker、数据库、队列、对象存储跑通。
- 先保证可靠任务执行，再追求服务数量。
- 不按菜单拆服务，按领域边界、数据归属和运行特征拆服务。
- 每个服务必须有清晰的数据所有权，禁止跨服务随意读写表。
- shared 库只共享通用工具、DTO、事件契约和客户端，不共享所有 ORM Model。
- Beta1.0 是本地云原生，不直接等同生产级 SaaS。

## 3. 目标架构

### 3.1 Beta1.0 推荐架构

```text
Browser
  |
  v
Ingress / Nginx
  |
  v
gateway
  |
  +--> auth-svc
  +--> model-svc
  +--> file-svc
  +--> task-svc
  +--> content-svc
  +--> interview-svc
  +--> research-svc

task-svc  <--> RabbitMQ <--> worker
worker    <--> model-svc
file-svc  <--> MinIO
services  <--> PostgreSQL
services  <--> Redis

Observability:
Prometheus + Grafana + Loki + OpenTelemetry
```

### 3.2 本地部署形态

Beta1.0 分两种本地运行方式：

| 形态 | 目标 | 说明 |
|------|------|------|
| Docker Compose | 日常开发和快速启动 | 本地最优先，便于调试 |
| kind / Kubernetes | 学习云原生部署 | 模拟集群、服务发现、探针、滚动更新 |

不建议一开始只写 K8s YAML 而忽略 Docker Compose。个人项目需要快速反馈，Compose 更适合作为第一落地点。

### 3.3 生产级目标形态

未来上线时再考虑：

- 云托管 PostgreSQL
- 云对象存储或 MinIO
- 托管 RabbitMQ / Redis
- Ingress Controller + TLS
- 镜像仓库
- GitHub Actions 自动构建和部署
- 灰度发布和回滚策略

## 4. 服务边界与职责

### 4.1 服务拆分原则

服务拆分不按页面菜单，而按以下标准：

- 是否拥有独立的数据模型和生命周期？
- 是否有独立的状态机或任务编排？
- 是否需要不同的扩缩容策略？
- 是否依赖不同的外部系统？
- 是否能独立发布而不频繁牵动其他服务？

如果只是 Prompt 模板不同，不拆成单独微服务。

### 4.2 Beta1.0 服务清单

| 服务 | 职责 | 数据所有权 | 说明 |
|------|------|------------|------|
| gateway | 统一入口、路由、认证校验、限流、请求 ID | 无业务表 | Beta 初期可用 FastAPI，后续可换 Kong/Envoy |
| auth-svc | 用户、登录、Token、权限、API Key | `auth_schema` | 即使个人使用，也为未来上线预留 |
| model-svc | 模型配置、Provider、Prompt 模板、模型测试 | `model_schema` | 不负责执行长任务 |
| task-svc | 任务元数据、状态机、任务查询、重试、取消 | `task_schema` | 不放具体业务规则 |
| worker | 从队列消费任务、执行模型调用、写回任务结果 | `task_schema` 受控写 | 可与 task-svc 同代码库、不同部署 |
| file-svc | 文件上传、解析、导出、对象存储访问 | `file_schema` + MinIO | 文件解析可异步化 |
| content-svc | 内容创作工作流、文体表单、Prompt 组装 | `content_schema` | 不按小红书/知乎/歌词拆服务 |
| interview-svc | 简历分析、问题生成、答题评价、复盘流程 | `interview_schema` | 有独立流程和状态，保留独立服务 |
| research-svc | 网页抓取、站内发现、arXiv 拉取、日报编排 | `research_schema` | 与外部站点和 arXiv API 强相关 |

### 4.3 避免分布式单体

`task-svc` 不是所有业务逻辑的收纳箱。它只负责通用任务能力：

- 任务创建、状态流转、重试、取消、超时、查询。
- 把任务投递到 RabbitMQ。
- 保存执行结果和运行日志。

业务规则归属业务服务：

- content-svc 负责内容创作字段、文体策略、Prompt 组装。
- interview-svc 负责面试流程和评价结构。
- research-svc 负责抓取策略、来源筛选、arXiv 方向和日报逻辑。

如果所有业务服务只是薄薄转发到 task-svc，task-svc 会变成分布式单体，应当避免。

### 4.4 服务调用关系

```text
Frontend -> Gateway
  -> content-svc / interview-svc / research-svc
      -> task-svc
          -> RabbitMQ
              -> worker
                  -> model-svc
```

模型调用链路统一走 model-svc，避免 API Key、Provider 配置、模型重试逻辑散落在多个服务中。

## 5. 服务内分层与设计模式

### 5.1 分层策略

不是所有服务都上完整 DDD。按复杂度分级：

| 等级 | 服务 | 分层模式 |
|------|------|----------|
| L1 简单 CRUD | auth-svc, model-svc | API -> Service -> Repository |
| L2 编排型 | task-svc, file-svc, content-svc, research-svc | API -> UseCase -> Domain -> Repository/Client |
| L3 状态流程型 | interview-svc | 整洁架构 + 局部 DDD 战术模式 |

### 5.2 标准服务结构

```text
service-name/
  app/
    main.py
    api/             # HTTP 路由、请求响应适配
    usecases/        # 用例编排
    domain/          # 领域对象、状态机、规则
    repositories/    # 数据访问
    clients/         # 调其他服务的客户端
    services/        # 外部系统适配，如模型、文件、队列
    core/            # 配置、日志、异常、依赖注入
  tests/
  Dockerfile
  pyproject.toml
```

### 5.3 shared 库边界

可以共享：

- 通用错误码
- 请求 ID、日志、配置加载工具
- OpenAPI 生成的 client
- Pydantic DTO
- 事件契约

不建议共享：

- 所有服务的 SQLAlchemy ORM Model
- 业务 Repository
- 业务 Service
- 数据库 Session

原因：共享 ORM 会让所有服务重新耦合到一套数据模型，破坏微服务边界。

## 6. 服务间通信与任务队列

### 6.1 同步通信

服务间同步调用采用 HTTP + JSON：

- 与 FastAPI / OpenAPI / Pydantic 天然匹配。
- 易调试，`curl` 和浏览器即可验证。
- 本项目服务数量少，同集群内网络开销不是瓶颈。

gRPC 暂不作为默认方案。未来只有在特定高频链路出现明确性能瓶颈时，再对单条链路引入 gRPC。

### 6.2 异步任务队列

长任务和可靠事件不使用 Redis Pub/Sub，改为：

> RabbitMQ + Celery Worker

选择原因：

- 支持持久化队列。
- 支持 ack / nack。
- 支持失败重试。
- 支持死信队列。
- 支持任务超时和取消策略。
- Python 生态成熟，适合 AI 长任务。

Redis 保留用于：

- 缓存模型配置和 Prompt 模板。
- 限流计数。
- 短期会话状态。
- 分布式锁（谨慎使用）。

### 6.3 任务生命周期

```text
业务服务创建任务
  -> task-svc 写入 tasks 表，状态 queued
  -> task-svc 投递 RabbitMQ
  -> worker 消费任务，状态 running
  -> worker 调 model-svc / 外部模型
  -> worker 写结果，状态 succeeded / failed
  -> task-svc 提供查询、SSE、导出
```

### 6.4 幂等与重试

任务请求需要包含：

- `idempotency_key`
- `task_type`
- `user_id`
- `payload_hash`

重试策略：

- 短暂网络失败：指数退避重试。
- 模型限流：按 Provider 维度退避。
- 业务参数错误：不重试，直接 failed。
- 多次失败：进入死信队列，允许人工重试。

## 7. 数据架构

### 7.1 数据库策略

Beta1.0 使用单 PostgreSQL 实例 + 多 schema：

```text
PostgreSQL
  auth_schema
  model_schema
  task_schema
  file_schema
  content_schema
  interview_schema
  research_schema
```

这是个人项目的成本折中，不等于完全的数据自治。

约束：

- 每个服务只拥有自己的 schema。
- 服务账号只授予对应 schema 权限。
- 禁止跨 schema join。
- 跨服务读取必须走 API 或事件。
- 每个服务维护自己的 Alembic migration。

### 7.2 对象存储

文件和导出报告不再依赖本地磁盘，改用 MinIO：

- 原始上传文件
- 解析后的中间文件
- 导出的 Markdown / PDF
- 长文本报告附件

数据库只保存元数据和对象 key。

### 7.3 数据一致性

| 场景 | 策略 |
|------|------|
| 创建任务并投递队列 | Outbox Pattern 或本地事务后可靠投递 |
| 任务执行结果写回 | worker 幂等更新任务状态 |
| 业务服务需要任务完成通知 | 订阅 RabbitMQ 事件或查询 task-svc |
| 跨服务事务 | 避免；必要时用 Saga + 补偿 |

## 8. 技术选型

### 8.1 选型总览

| 层 | 选型 | 说明 |
|----|------|------|
| 后端语言 | Python 3.12 / 3.13 | 优先稳定生态，不默认追最新 3.14 |
| Web 框架 | FastAPI | 保留现有资产，适合 OpenAPI |
| 后端运行 | uvicorn / gunicorn | 容器内按服务配置 worker |
| ORM | SQLAlchemy 2.x | async 可逐步引入，不一次性重写 |
| 迁移 | Alembic | 每服务独立 migration |
| 数据库 | PostgreSQL 16 | 替代 SQLite |
| 队列 | RabbitMQ + Celery | 可靠长任务 |
| 缓存 | Redis 7 | 缓存、限流、短状态 |
| 对象存储 | MinIO | 本地 S3 兼容存储 |
| 前端 | Next.js 16 + React 19 | 保留现有前端 |
| 容器 | Docker | 每服务独立镜像 |
| 本地编排 | Docker Compose | 日常开发主入口 |
| K8s 开发 | kind + Helm/Kustomize | 学习云原生 |
| 可观测性 | OpenTelemetry + Prometheus + Grafana + Loki | 指标、链路、日志 |
| CI/CD | GitHub Actions | 测试、构建、扫描、推送镜像 |

### 8.2 语言选择

Beta1.0 继续使用 Python：

- 已有大量 Python 代码可复用。
- 项目核心瓶颈是外部模型网络 IO，不是 CPU 计算。
- AI SDK、爬虫、文档解析生态更适合 Python。

Go / Java 可以作为未来局部替换方案：

- 高频、低延迟模型网关可考虑 Go。
- 企业认证、权限、网关治理若复杂化，可考虑 Java / Spring 生态。

### 8.3 网关选择

Beta1.0：

- Nginx Ingress 负责南北向入口。
- FastAPI gateway 负责业务路由、认证上下文、聚合接口。

未来生产：

- 若需要 API Key、租户配额、复杂限流、审计和插件生态，迁移 Kong / Envoy / APISIX。

## 9. 安全设计

即使当前是个人使用，也要按未来上线预留安全基线。

### 9.1 身份与权限

- 用户登录：JWT access token + refresh token。
- 密码存储：Argon2 / bcrypt。
- 权限：个人版先使用 owner/admin 简化模型，未来扩展 RBAC。
- 服务间调用：内部 service token 或 mTLS 预留。

### 9.2 Secret 管理

- 本地：`.env.local` + Docker Compose secrets。
- K8s：Secret，不把 API Key 写入镜像或 ConfigMap。
- 未来：External Secrets / 云厂商 Secret Manager。

### 9.3 网络与接口安全

- Gateway 统一 CORS。
- Rate limit 按用户、IP、模型 Provider 维度限制。
- 上传文件大小限制和类型校验。
- 防止路径穿越。
- SSRF 防护：爬虫限制私网 IP、metadata 地址、file 协议。
- Prompt 注入风险提示和来源隔离。

### 9.4 审计

记录以下行为：

- 登录和失败登录。
- 模型配置创建/修改。
- API Key 修改。
- 文件上传和删除。
- 导出报告。
- 长任务重试、取消、失败。

## 10. 可观测性与运维

### 10.1 日志

- 所有服务输出 JSON 日志。
- 日志字段包含：`trace_id`、`request_id`、`user_id`、`service`、`route`、`task_id`、`duration_ms`、`status`。
- 使用 Loki 或 OpenSearch 收集日志。

### 10.2 指标

Prometheus 指标至少包括：

- HTTP 请求总数、错误数、延迟直方图。
- 队列长度、消费速率、失败任务数、死信数量。
- 模型调用次数、失败率、平均耗时、token 使用量。
- 文件解析耗时和失败率。
- 爬虫成功率、来源失败分布。

### 10.3 链路追踪

使用 OpenTelemetry：

```text
gateway -> business-svc -> task-svc -> RabbitMQ -> worker -> model-svc -> external model API
```

每个任务和模型调用要能从 trace 中串起来。

### 10.4 告警

基础告警：

- API 5xx 比例超过阈值。
- 任务队列积压持续增长。
- 任务失败率异常。
- 模型 Provider 超时或限流。
- PostgreSQL / RabbitMQ / Redis 不可用。
- 磁盘或对象存储容量不足。

## 12. 高可用、高并发、高性能设计

### 12.1 高可用

- 无状态 API 服务多副本。
- Worker 可水平扩展。
- K8s readiness / liveness / startup probes。
- 优雅关闭：停止接收新任务，等待当前任务完成或重新入队。
- PostgreSQL、RabbitMQ、Redis 初期单节点，本地学习为主；生产再引入高可用。

### 12.2 高并发

- API 层 async HTTP。
- 长任务进入 RabbitMQ，不阻塞 API 请求。
- Worker 并发数按模型 Provider 限流配置。
- PostgreSQL 连接池 + PgBouncer。
- Gateway 限流保护后端和模型额度。

### 12.3 高性能

当前阶段不承诺固定 QPS，先建立可压测指标：

| 指标 | Beta 目标 |
|------|-----------|
| API P95 延迟 | < 300ms（不含 AI 生成） |
| 任务状态查询 P95 | < 200ms |
| 模型任务失败率 | 可观测、可重试 |
| 队列积压 | 可观测、可告警 |
| 文件解析失败 | 可定位错误原因 |

性能优化策略：

- Prompt 模板和模型配置缓存。
- 数据库关键字段索引。
- 大报告对象存储化。
- 流式输出减少等待感。

---

## 13. 风险与应对

| 风险 | 等级 | 应对 |
|------|------|------|
| 微服务拆分过细，形成分布式单体 | 高 | 以数据边界和状态机为拆分标准，限制 task-svc 职责 |
| 个人维护多个服务成本高 | 高 | Docker Compose 优先，服务数量控制在必要范围 |
| 共享 ORM 导致重新耦合 | 高 | shared 不放全量 ORM，服务独立 schema 和 migration |
| 队列任务丢失 | 高 | RabbitMQ durable queue + ack + retry + DLQ |
| SQLite 迁移 PostgreSQL 数据差异 | 中 | Alembic migration + 数据校验脚本 |
| 外部模型限流和费用失控 | 中 | Provider 限流、预算统计、失败重试上限 |
| 爬虫 SSRF / 不可信网页 | 中 | URL 白名单/黑名单、私网 IP 拦截、超时限制 |
| K8s 学习曲线 | 中 | 先 Compose，再 kind，最后云环境 |
| 安全体系不足 | 中 | 认证、Secret、审计、网络策略分阶段补齐 |

## 14. 阶段路线图

### 阶段 0：文档和边界确认

- 明确服务边界。
- 明确 shared 库边界。
- 确认 PostgreSQL schema 策略。
- 确认 RabbitMQ + Celery 任务模型。

### 阶段 1：本地 Compose 云原生底座

- PostgreSQL 替换 SQLite。
- RabbitMQ 接管长任务。
- Redis 用于缓存和限流。
- MinIO 接管文件和导出。
- API / Web / Worker 容器化。

### 阶段 2：服务拆分

- gateway
- auth-svc
- model-svc
- task-svc + worker
- file-svc
- research-svc
- content-svc
- interview-svc

### 阶段 3：可观测性和安全

- OpenTelemetry Trace。
- Prometheus + Grafana。
- Loki 日志。
- 认证授权。
- Secret 管理。
- 审计日志。

### 阶段 4：Kubernetes 本地集群

- kind 部署。
- Helm/Kustomize。
- readiness/liveness probes。
- HPA 验证。
- 滚动更新和回滚。

### 阶段 5：小规模上线准备

- 云数据库或可靠备份。
- TLS 和域名。
- 镜像仓库。
- CI/CD。
- 数据备份恢复演练。
