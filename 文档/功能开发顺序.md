# ChenSage AgentOS Beta1.0 功能开发顺序

> 版本：Beta1.0  
> 修订日期：2026-07-09  
> 目标：按 MVP 已验证功能逐步迁移到 AgentOS 架构，先跑通任务主链路，再恢复并增强具体产品功能。

---

## 1. 排序原则

Beta1.0 的开发顺序遵循四个原则：

- 先主链路，后复杂能力：先让任务能创建、入队、执行、更新状态、查看结果。
- 先低外部依赖，后高外部依赖：先做内容创作和模型设置，再做网页、RSS、arXiv、批量抓取。
- 先统一底座，后功能扩展：任务中心、模型设置、提示词模板、文件管理是多个功能共用底座。
- 每个功能都进入 task-svc：不要绕过统一任务中心做孤立页面。

---

## 2. 总体顺序

推荐顺序：

```text
0. 基础项目骨架和本地依赖
1. 任务中心与任务执行主链路
2. 模型设置
3. 提示词模板
4. 知识库基础结构
5. 对话式生产窗口
6. 内容创作与改写
7. 内容评价与学习反馈
8. 生成版本管理
9. 历史任务与 Markdown 导出
10. 文件管理与解析
11. 模拟面试
12. 信息搜集
13. arXiv 日报
14. 活记忆、知识库权重、提示词优化和观测增强
```

## 3. 阶段 0：基础项目骨架和本地依赖

### 目标

让项目具备可持续开发的基本形态。

### 开发内容

- 前端目录：`apps/web`。
- 后端服务目录：`services/gateway`、`services/task-svc`、`services/model-svc`、`services/agent-svc`。
- Worker 目录：`workers/agent-worker`。
- 共享契约目录：`packages/shared`。
- 本地基础设施目录：`infra/docker`。
- 配置目录：`config/app`、`config/models`、`config/prompts`。
- 环境变量示例：`.env.example`、`infra/docker/.env.example`。
- Docker Compose 准备 PostgreSQL、RabbitMQ、Redis、MinIO。

### 完成标准

- 本地可以启动基础依赖。
- 前端、后端、worker 目录边界清晰。
- `.env.example`、README、基础配置结构齐全。
- 大模型 API Key 只通过 `model-svc` 配置边界读取，真实密钥不进入 Git。

### 当前落地方式

阶段 0 先采用“基础依赖 Docker Compose + 业务服务本机进程”的方式：

```bash
make setup-env
make infra-up
make check-stage0
make compile-services
```

本地服务端口约定：

| 模块 | 启动命令 | 地址 |
|------|------|------|
| gateway | `make run-gateway` | `http://localhost:8000` |
| task-svc | `make run-task-svc` | `http://localhost:8011` |
| model-svc | `make run-model-svc` | `http://localhost:8012` |
| agent-svc | `make run-agent-svc` | `http://localhost:8013` |
| knowledge-base-svc | `make run-knowledge-base-svc` | `http://localhost:8014` |
| agent-worker | `make run-agent-worker` | 消费队列：`agent.tasks` |

Docker Compose 在阶段 0 只负责 PostgreSQL + pgvector、RabbitMQ、Redis、MinIO 和 MinIO bucket 初始化。gateway、task-svc、model-svc、agent-svc、agent-worker 后续进入端到端联调时再加入 Compose 镜像构建。

## 4. 多设备开发与基础服务策略

如果经常在两台电脑之间切换开发，基础服务要采用“可复制、可重建、少依赖本机状态”的策略。

### 核心原则

```text
代码同步：GitHub
基础服务：Docker Compose
本地配置：.env，不提交
示例配置：.env.example，提交
开发数据：可重建，必要时导出 / 导入
生产或长期数据：后续单独放云端或服务器
```

### 每台电脑的初始化方式

每台电脑都安装 Docker Desktop，然后在项目中执行：

```bash
git pull
cp .env.example .env
cd infra/docker
cp .env.example .env
docker compose up -d
```

启动的基础服务：

```text
PostgreSQL + pgvector
RabbitMQ
Redis
MinIO
```

### 配置和密钥

- 真实 `.env` 不提交。
- 大模型 API Key、数据库密码、MinIO 密钥都放本机 `.env`。
- GitHub 只提交 `.env.example` 和 `*.example.yaml`。
- `model-svc` 是唯一读取模型 Provider Secret 的服务。
- 两台电脑可以使用不同 `.env`，但代码和配置结构保持一致。

### 开发数据

默认情况下，两台电脑的本地数据库和 MinIO 数据不需要同步。

原因：

- 本地任务、解析文件、测试结果属于开发数据。
- 每台电脑可以通过 migration 和 seed 数据重建环境。
- 避免为了同步本地数据引入额外复杂度。

后续如需同步少量测试数据，可以增加：

```text
scripts/seed_dev_data.py
scripts/db_dump.sh
scripts/db_restore.sh
scripts/minio_export.sh
scripts/minio_import.sh
```

推荐先实现 seed 数据，而不是同步完整本地数据库。

### 日常切换流程

电脑 A：

```bash
git pull
# 开发
git add .
git commit -m "..."
git push
```

电脑 B：

```bash
git pull
cd infra/docker
docker compose up -d
```

如果 `.env.example`、migration 或依赖发生变化，再按 README 更新本机 `.env`、数据库和本地依赖。

### 未来可选方案

项目稳定后，可以考虑一台云服务器运行共享开发依赖：

```text
远程 PostgreSQL
远程 RabbitMQ
远程 Redis
远程 MinIO
```

两台电脑都连接远程基础服务。但 Beta 初期不建议这么做，优先使用本地 Docker Compose，保证开发便宜、快速、离线可用。

## 5. 阶段 1：任务中心与任务执行主链路

### 为什么先做

任务中心是所有功能的共同入口。内容创作、面试、信息搜集、arXiv 日报、文件解析和导出都应该是 task，而不是各自维护一套状态。

### 开发内容

- `task-svc`：
  - task 创建。
  - task 状态机：`queued`、`running`、`succeeded`、`failed`、`cancelled`。
  - task event。
  - task result。
  - retry 和 cancel 的接口预留。
- RabbitMQ：
  - task 队列。
  - worker 消费。
- `agent-worker`：
  - 消费任务。
  - 执行一个最小 stub 任务。
  - 写回状态和结果。
- `apps/web`：
  - 任务创建页。
  - 任务列表页。
  - 任务详情页。

### 完成标准

- 用户能在前端创建一个任务。
- 任务进入队列后被 worker 消费。
- 前端能看到任务状态从 `queued` 到 `running` 再到 `succeeded` 或 `failed`。
- 任务详情页能展示事件和最终结果。

---

## 6. 阶段 2：模型设置

### 为什么第二个做

内容创作、面试、信息搜集摘要和日报生成都依赖模型。先把模型配置统一起来，后续 Agent 不直接处理 API Key。

### 开发内容

- `model-svc`：
  - OpenAI-compatible API base URL。
  - API Key 保存和脱敏展示。
  - 默认模型配置。
  - 连通性测试。
  - 简单 chat completion 调用。
- `apps/web`：
  - 模型设置页。
  - 连通性测试按钮。
  - 默认模型选择。

### 完成标准

- 用户可以配置 OpenAI-compatible Provider。
- 可以测试连通性。
- `agent-worker` 或 `agent-svc` 可以通过 `model-svc` 完成一次最小模型调用。
- 日志不输出完整 API Key。

---

## 7. 阶段 3：提示词模板

### 为什么第三个做

原 MVP 的内容创作、信息搜集、arXiv 日报都依赖模板。模板先统一，后续功能就不是散落的硬编码 Prompt。

### 开发内容

- `agent-svc` 内 prompt registry：
  - 模板列表。
  - 模板详情。
  - 按任务类型分类。
  - 模板变量 schema。
  - 模板版本字段预留。
- `apps/web`：
  - 模板列表页。
  - 模板编辑页。
  - 模板变量预览。

### 完成标准

- 可以为不同任务类型维护模板。
- 内容创作任务可以选择模板。
- 模板变量可以被 task input 填充。

---

## 8. 阶段 4：知识库基础结构

### 为什么提前做

对话式生产窗口需要根据任务调取历史内容、资料来源、用户偏好、高质量案例和评价经验。知识库先具备最小结构，后续内容创作和评价反馈才不会只是一次性输出。

### 开发内容

- `knowledge-base-svc` 或 `living-memory-svc` 内的知识库模块：
  - knowledge item。
  - knowledge chunk。
  - source refs。
  - content version。
  - quality score。
  - tags / task_type / source_type。
  - pgvector embedding 字段预留。
- `context-engine`：
  - 按任务类型选择知识库范围。
  - 返回来源、质量分、状态和适用范围。
- `apps/web`：
  - 知识库侧栏原型。
  - 来源和历史内容引用展示。

### 完成标准

- 可以保存历史生成内容的版本。
- 可以保存资料来源和摘要。
- 可以按任务类型检索知识条目。
- 检索结果带来源和状态，不直接污染长期记忆。

### 当前落地方式

阶段 4 先实现 `knowledge-base-svc` 的进程内最小知识库结构：

- `/knowledge-items` 支持创建、列表筛选和详情读取。
- `/knowledge-items/{item_id}/chunks` 支持追加知识片段。
- `/knowledge-items/{item_id}/sources` 支持追加资料来源。
- `/knowledge-items/search` 支持按 `task_type`、`tags`、`source_type`、`status`、`quality_score` 和关键词检索。
- `embedding` / `embedding_model` 字段预留给后续 PostgreSQL + pgvector。

这一步先稳定服务边界和前端引用展示，后续再替换为数据库实现，并接入 `context-engine`。

## 9. 阶段 5：对话式生产窗口

### 为什么在内容创作前做

后续所有功能都可以从统一对话入口进入。用户不必先选择功能，而是直接描述目标，由系统理解任务、调取知识、选择 Agent 和模板。

### 开发内容

- `conversation-agent`：
  - 理解用户目标。
  - 判断任务类型。
  - 提出澄清问题。
  - 选择知识库范围。
  - 选择 Agent 和模板。
- `apps/web`：
  - 中间对话式生产窗口。
  - 左侧知识库 / 历史任务 / 模板入口。
  - 右侧任务上下文、知识来源、评价反馈和版本历史。

### 完成标准

- 用户可以通过对话创建内容生产任务。
- 系统能识别至少 `content_generation` 和 `content_rewrite` 两类任务。
- 对话窗口能展示本次任务使用的知识来源和模板。

---

## 10. 阶段 6：内容创作与改写

### 为什么优先恢复这个产品功能

内容创作链路短、外部依赖少，最适合作为第一个真实 Agent 功能。它能验证任务、模板、模型、知识库、对话入口和评价反馈的主要边界。

### 开发内容

- `content-agent`：
  - 内容生成。
  - 内容改写。
  - 风格、平台、长度、语气参数。
  - 支持论文、专利、小说、剧本、歌词、脱口秀稿 / 单口喜剧稿、小红书、知乎、公众号等类型。
- `task-svc`：
  - task_type：`content_generation`、`content_rewrite`。
- `knowledge-base-svc`：
  - 检索历史高分内容。
  - 检索用户风格偏好。
- `apps/web`：
  - 内容创作对话流。
  - 内容类型选择。
  - 模板选择。
  - 结果预览。

### 完成标准

- 用户能通过对话或表单创建内容创作任务。
- 任务通过模板、知识库和模型生成结果。
- 结果进入统一历史任务和内容版本。
- 支持至少 Markdown 形式的结果展示。

---

## 11. 阶段 7：内容评价与学习反馈

### 为什么必须紧跟内容创作

系统需要知道“为什么这次生成好或不好”。评价不能只是打分，还要给理由、定位问题、提出修改建议，并把可复用经验沉淀成学习候选。

### 开发内容

- `eval-svc`：
  - 分维度评分。
  - 每个分数的理由。
  - 具体问题位置。
  - 可执行修改建议。
  - 值得保留的优点。
  - learning candidates。
- `memory-agent`：
  - 判断哪些评价经验可沉淀。
  - 将长期偏好或模板经验置为待确认。
- `apps/web`：
  - 评分面板。
  - 理由面板。
  - 问题定位列表。
  - 修改建议列表。
  - “按建议优化”按钮。

### 完成标准

- 每次内容生成后都有 eval report。
- eval report 至少包含 `scores`、`score_reasons`、`issue_locations`、`revision_advice`。
- 用户可以选择按建议重新生成。
- 可沉淀经验进入待确认状态，而不是自动长期生效。

## 12. 阶段 8：生成版本管理

### 开发内容

- `task-svc` / `knowledge-base-svc`：
  - content version。
  - version diff。
  - accepted version。
  - regeneration reason。
- `apps/web`：
  - 版本历史。
  - 对比查看。
  - 选择采用某一版。
  - 从某一版继续修改。

### 完成标准

- 一次任务可以保存多个生成版本。
- 每个版本关联输入、模板、知识来源、模型配置和评价报告。
- 用户可以选择最终采用版本。

---

## 13. 阶段 9：历史任务与 Markdown 导出

### 为什么此时做

内容创作、评价和版本管理完成后，历史任务和导出才能承载完整内容生产闭环。

### 开发内容

- `task-svc`：
  - 历史任务筛选。
  - 任务重试。
  - 任务结果查询。
- `tool-registry` 或导出模块：
  - Markdown export。
- `file-svc`：
  - 导出产物元数据。
  - MinIO object key。
- `apps/web`：
  - 历史任务页。
  - 重试按钮。
  - 导出 Markdown 按钮。

### 完成标准

- 所有内容创作任务可在历史任务中查看。
- 失败任务可重试。
- 成功任务可导出 Markdown。
- 导出内容可选择最终采用版本。

---

## 14. 阶段 10：文件管理与解析

### 为什么放在面试和信息搜集前

模拟面试依赖简历文件，信息搜集也依赖 PDF / TXT / MD 解析。先做文件底座，可以复用到多个功能。

### 开发内容

- `file-svc`：
  - 文件上传。
  - 文件元数据。
  - MinIO 存储。
  - 解析状态。
- `tool-registry`：
  - PDF parse。
  - DOCX parse。
  - TXT / MD parse。
- `knowledge-base-svc`：
  - 文件解析结果可选择进入知识库。
- `apps/web`：
  - 文件列表页。
  - 上传入口。
  - 解析结果预览。

### 完成标准

- 用户能上传 PDF、DOCX、TXT、MD。
- 文件能被解析为文本。
- 解析结果可以被后续任务引用。
- 用户可以选择是否把解析结果沉淀到知识库。

---

## 15. 阶段 11：模拟面试

### 开发内容

- `interview-agent`：
  - 简历分析。
  - 岗位描述分析。
  - 面试问题生成。
  - 回答评价。
  - 复盘报告。
- `eval-svc`：
  - 回答完整性、匹配度、表达质量评分。
  - 评分理由、问题定位、改进建议。
- `knowledge-base-svc`：
  - 面试题库。
  - 岗位评价标准。
  - 高质量回答案例。
- `apps/web`：
  - 简历选择 / 上传。
  - JD 输入。
  - 问题列表。
  - 回答输入。
  - 复盘报告页。

### 完成标准

- 用户可以基于简历和 JD 创建模拟面试任务。
- 系统能生成问题。
- 用户回答后能得到评价、理由和复盘报告。
- 面试结果进入历史任务和可治理知识库。

## 16. 阶段 12：信息搜集

### 为什么后置

信息搜集涉及网页访问、RSS、JSON、PDF、批量任务和站内发现，外部不确定性更高。等任务、文件、模板、模型、知识库和评价反馈稳定后再做更稳。

### 开发内容

- `research-agent`：
  - 单 URL 摘要。
  - PDF 信息提取。
  - JSON 数据提取。
  - RSS 拉取和摘要。
  - 批量多任务。
  - 站内信息发现。
  - 汇总报告。
- `tool-registry`：
  - web fetch。
  - RSS parse。
  - JSON parse。
  - site discovery。
- `policy-svc`：
  - 外部域名白名单。
  - SSRF 防护。
- `knowledge-base-svc`：
  - 资料来源、摘要、引用和可信度记录。
- `apps/web`：
  - 信息搜集任务创建页。
  - 批量任务进度页。
  - 汇总报告页。

### 完成标准

- 支持单 URL / PDF / JSON / RSS 信息搜集。
- 支持批量任务。
- 支持生成 Markdown 汇总报告。
- 外部请求经过 policy-svc 规则。
- 用户可选择将资料来源和摘要沉淀到知识库。

  - 论文库。
  - 收藏论文。
  - 研究方向长期资料。
- `apps/web`：
  - 研究方向页。
  - arXiv 拉取任务页。
  - 收藏列表。
  - 日报生成页。

### 完成标准

- 用户可以配置研究方向。
- 可以按日期和篇数拉取论文。
- 可以收藏论文。
- 可以按范围生成 Markdown 日报。
- 高价值论文可进入知识库，供内容创作和对话窗口引用。

## 18. 阶段 14：活记忆、知识库权重、提示词优化和观测增强

### 开发内容

- `living-memory-svc`：
  - 任务偏好沉淀。
  - 用户确认长期记忆。
  - 冲突检测。
  - 过期降权。
- `knowledge-base-svc`：
  - 知识质量分。
  - 检索权重。
  - 高质量案例治理。
- `prompt-optimizer`：
  - 从多次评价报告中提出模板优化建议。
  - 记录建议来源和证据。
  - 用户确认后生效。
- 可观测：
  - task trace。
  - loop step trace。
  - tool call trace。
  - token / cost。
  - eval report。
  - knowledge retrieval trace。

### 完成标准

- 用户可以查看、确认、冻结、删除记忆。
- 用户可以查看知识条目来源、质量分和使用记录。
- 复杂任务生成 eval report。
- 任务详情页能展示关键 trace、知识来源和成本信息。
- 提示词优化建议可审核、可采纳、可回滚。

## 19. 第一条建议实现链路

最推荐从这条链路开始：

```text
模型设置
  -> 提示词模板
  -> 知识库最小结构
  -> 对话式生产窗口
  -> 内容创作任务
  -> worker 执行
  -> model-svc 调用模型
  -> task-svc 写回结果
  -> eval-svc 生成评分、理由、问题定位、修改建议
  -> 用户按建议优化并生成第二版
  -> 采用最终版本
  -> 历史任务查看
  -> Markdown 导出
```

它覆盖了 Beta1.0 的核心底座，也能最快形成真正的内容生产闭环。
